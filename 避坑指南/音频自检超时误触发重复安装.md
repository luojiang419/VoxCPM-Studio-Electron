# 音频自检超时误触发重复安装

表现：安装器长时间显示“加载并检查音频组件”循环动画，模型迟迟不下载；日志可能已有成功安装和自检记录，重试后却又重装 pip 与整套音频依赖。

根因：完整 PROBE 在模型下载之前串行加载 torch、FunASR、wetext 等框架。首次冷加载受磁盘、杀毒扫描和系统负载影响；quiet 输出隐藏了当前步骤。异常处理没有区分超时与确实缺失/损坏，超时同样进入强制重装，进一步延长等待。

解决：模型先于完整导入检查和补齐；自检用无缓冲逐行阶段事件报告具体模块及耗时。子进程超时使用独立错误码，停止并保留已安装资源，允许重试；实际导入/版本/依赖闭包失败继续修复。已有成功缓存仍快速复用，不重复完整导入或模型哈希。

验证：任务 027 的 41 项 Node 回归、类型检查、生产构建及真实 RTX 4070 Ti SUPER/cu126 自检通过。测试覆盖缺失模型先下载、已有/托管环境超时不安装、不写假就绪记录、真实子进程分片中文输出与超时错误码。证据位于 `builds/installer-probe-diagnosis/`，本机热缓存自检耗时不能冒充冷启动性能。

后续用户澄清了音乐模型下载起步太晚：`ComponentService.prepare` 还有视频组件 → 3.46 GiB 音乐运行包下载/安装 → 音乐模型的串行顺序。基础音频修复不会改变这条链路，不能用基础模型验收结果宣称音乐问题也已解决。音乐模型文件下载已前置到可选环境准备之前，音乐自检超时也不再重装完整运行包。新增顺序、暂停续传和超时门禁测试后共 44 项通过。

继续定位环境检测本身：原 PROBE 导入 Gradio、FunASR、wetext 等框架，API 启动又在新 Python 进程导入同一批模块；FunASR 包入口会递归加载子模块，wetext 包入口会读取多种 FST 规则。预检只需要核对包入口/版本以及实际 torch、torchaudio、numpy、soundfile 和 CUDA 运算，框架实际导入由后续 API 健康握手覆盖，不应重复执行。

环境就绪记录还将模型与 Python 文件放在同一个失效条件里。新增独立环境签名/文件指纹，模型变化仅重校模型，环境入口、版本、驱动、路径变化仍使环境缓存失效；内容不变不重写 `_pth`。原合并 `files` 字段继续保留，兼容安装修复器。

同机同 Python 顺序计时：入口/版本检查 185ms，旧完整 PROBE 16903ms，新 PROBE 2806ms，pip check 791ms；新 PROBE 的 sys.modules 中没有 Gradio/FunASR/wetext。该结果有系统文件缓存，不能冒充首次冷启动或完整应用启动时间。48 项回归覆盖模型缺失不再检查 CUDA/pip、环境自身变化仍失效与服务失败不假报就绪。
