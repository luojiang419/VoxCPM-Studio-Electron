# 启动按需校验与延迟导入

表现：模型权重虽然已经按需加载，每次启动仍停留在“音频服务”或“功能自检”，工作区无法先进入。

根因：主进程等待全部所选组件检查，音乐环境每次启动独立 probe；基础 API 导入 `studio_app` 时会加载 Gradio、Torch、FunASR 和模型类。单纯取消模型哈希检查不能消除这些耗时。LoRA 列表读取也可能通过构造 `LoRAConfig` 间接导入 Torch。

解决：正常启动先显示工作区，`RuntimeService.launch` 只定位已有 Python；基础 API 使用 `VOXCPM_LAZY_STARTUP=1` 延迟导入。模型在语音生成、识别、降噪或音乐生成入口单独校验，并缓存文件哈希与时间戳。LoRA 列表读取原配置字典，使用时才创建模型配置类。运行摘要显示“使用时检测”，不把尚未检测误报为无显卡。

安装器和显式“保存并准备”必须继续走完整准备，并以 `VOXCPM_LAZY_STARTUP=0` 保留真实框架导入和组件自检；正常启动不得伪造组件就绪凭证。缺少模型的识别请求需要映射为含修复提示的 HTTP 400，不能只抛出后端异常。后端进程提前退出时立即结束连接等待，并读取日志尾部显示原因。

验证：`scripts/smoke_lazy_startup.cjs` 使用实际 Electron 主进程和实际 API，模型全部缺失且存在 LoRA 时仍能进入工作区；检查 `sys.modules` 无 Torch/Gradio/FunASR/core；调用 ASR 才返回模型缺失提示，错误进程及时显示失败。首次使用的哈希缓存、同大小损坏、取消及路径约束由 `tests/test_studio_resources.py` 覆盖。
