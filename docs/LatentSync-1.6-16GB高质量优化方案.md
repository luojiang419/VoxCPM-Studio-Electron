# LatentSync 1.6：16 GB 显卡高质量优化方案

状态：设计完成，尚未实施下述优化。2026-10-18；实现基线为 `d7b6708`，开发进度继续记录在 `开发任务/012-本地视频对口型与照片说话.md`。

## 目标和固定约束

面向16GB NVIDIA显卡，在显存预算内优先保持人脸细节、口型和时序一致性；允许增加处理时间。显存不足只调整同一1.6模型的执行方式，仍不足则停止，不自动切换1.5。

- 使用原版1.6权重、512×512脸部区域、完整16帧时序窗口和25fps时间轴。
- 不以缩小脸部分辨率、缩短时序窗口、降低引导强度或量化权重作为自动节省显存的方法。
- 默认引导强度1.5，种子可复现；30步作为高质量候选默认，保留20/30/50步对照。最终默认以口型、细节和闪烁实测决定，不假定步数越多效果必然越好。
- 生成分辨率指脸部区域，不代表把整幅画面变成512px。1080p原画面作为首轮验收；4K保留原分辨率需在流式还原后单独验收，不先宣称支持。
- 其他程序的显存不由本程序强制释放。生成前释放本程序TTS，训练/ASR互斥，给桌面和驱动留余量。

## 现有证据与瓶颈

本机RTX 4070 Ti SUPER 16GB，1.6独立入口的1.36秒样片、20步：61.56秒，PyTorch peak allocated 4848MiB、reserved 5630MiB。证据：`builds/lipsync-auto-validation/real-1.6/inference.json`。这是短片、单卡证据，不能推导120秒已稳定或其他16GB卡具有同样表现。

已实现FP16、VAE slicing、CPU人脸检测、生成脸部返回CPU、逐帧还原。空间和时间注意力已使用PyTorch SDPA；不把再次启用SDPA当作新增收益。SDPA是否使用高效内核仍由形状、显卡和运行时决定。

当前仍需处理的占用：

| 位置 | 当前行为 | 优化方向 |
| --- | --- | --- |
| 视频读取/对齐 | 整段视频解码为数组；全部人脸和矩阵集中缓存 | 有界流式解码、顺序对齐、必要时将小型缓存写盘 |
| 初始潜变量 | 为整段帧数创建GPU `all_latents` | 仅为当前窗口构造16帧潜变量 |
| 引导计算 | 无音频/有音频两路拼成batch=2推理 | 显存受限时两路串行，保留原引导公式 |
| 组件常驻 | Whisper、VAE、UNet同时在GPU | 按阶段驻留，音频编码完成后卸载Whisper |
| 生成结果 | 脸部在CPU累计，末尾拼接；还原帧再集中堆叠 | 当前窗口还原并交给编码器后立即释放 |
| 原画面还原 | 每帧原画面/遮罩参与GPU处理 | 限制单帧在途；压力模式把完整画面还原移至CPU |

仅把长视频裁成多个独立MP4再分别推理，不能解决单个16帧窗口的峰值，也容易重置音频上下文、种子和对齐状态。因此采用同一任务内的连续窗口处理。

## 方案一：有界流式渲染，作为所有档位基础

数据流：全局音频特征 → 顺序视频解码 → 连续对齐 → 当前16帧模型推理 → 逐帧还原 → FFmpeg编码 → 最后合入原始配音。

1. 用完整音轨计算全局音频特征，按全局帧号取特征。长音频特征可缓存到磁盘；不以截断音频、逐片重新识别替代全局时间轴。
2. 生产者队列只保留2～4个窗口，初版上限64帧；内存紧张时减到16/32帧。1080×1920的64帧uint8原画面约380MiB，避免120秒原画面一次占据约17.4GiB内存。
3. GPU始终只处理一个16帧窗口。读入预取可以与CPU处理交错，禁止并行运行两个UNet窗口来追求速度。
4. 当前窗口生成后，逐帧还原并写入持续运行的编码器；排空队列和未引用张量，不再累计整片 `synced_video_frames` / `np.stack(frames)`。
5. 最后不足16帧时，初版保持现有短尾窗口语义，只输出真实帧数；若引入补帧策略，必须作为行为变化单独比较，不暗中复制尾帧。
6. 首选将解码/帧率规范化与模型输入串起来，避免“先有损转码输入、再有损编码结果”的多次压缩。最终视频编码一次，合并音轨使用视频流复制。

文件组织可按64帧提交一个无损脸部缓存块，但64帧只是I/O单元，不改变16帧模型窗口。禁止为降低内存将输出放入无限增长的Python列表。

## 分片连续性：默认保持官方窗口划分

首版不新增重叠窗口和图像融合，沿用全局 `[0,16)、[16,32)…`。先确保分片前后的算法语义一致，避免把普通缓存分片变成新的生成算法。

必须延续的状态：

- **音频特征**：始终按全局帧号索引，保留窗口边缘所需的音频上下文，不在每个缓存块开始时归零。
- **初始噪声**：当前代码生成一张初始噪声后沿时间轴重复。优化后保留同一噪声模板，每窗口展开；不能每片重新抽取不同模板，也不能重新设置种子。
- **随机数流**：保持VAE采样的全局发生顺序。编码任务并发、CPU/GPU切换、断点恢复都可能改变随机序列，需分别记录与验证。CPU卸载不意味着允许随意把随机采样改到CPU。
- **人脸对齐**：保留 `AlignRestore.p_bias` 等平滑状态。缓存块交界不重建对齐器；检测到真实镜头切换时再有规则地重置。
- **扩散调度器**：每个官方16帧窗口按原逻辑建立相同的完整步序，不把上一个窗口的末尾扩散状态误传给下个窗口。

如果实测仍有明显16帧边界闪烁，再另做可选“连续性增强”：完整16帧滑动窗口、适量重叠、仅对齐后的脸部区域做融合。需要额外算力，可能产生嘴部重影；不能在未对比前默认开启，也不对整张原画面做交叉淡化。

## 方案二：保持质量的串行引导与前馈分块

标准档仍可使用当前batch=2引导。节省显存档将每一步拆为两次batch=1前向：先计算无音频噪声预测，再计算有音频预测，按原公式合成，随后只调用一次scheduler更新。

`noise = noise_uncond + guidance * (noise_audio - noise_uncond)`

- 权重、512分辨率、16帧、步数和guidance不变；重复调用之间只保留合成所需的小型噪声预测。
- 引导用的mask/ref/audio张量不要提前双份常驻。两次前向使用同一个当前潜变量和时间步，不能顺序更新两次潜变量。
- 模型必须处于eval/no_grad状态。浮点内核选择不同仍可能造成数值差异，先进行一步预测误差比较，再进行完整视频A/B，不承诺逐位相同。
- 每步有两次前向，但batch=1和batch=2吞吐不同，不能先宣称耗时恰好翻倍或显存减半。

若激活峰值仍高，下一步只对空间/时间模块的逐token前馈网络分块，沿不跨token依赖的维度执行，保持残差与归一化语义。注意力和16帧时间序列本身不切成独立小段。首版串行引导不达预算后再启用此项，避免同时改动过多导致质量回归难定位。

## 方案三：按阶段驻留与极限低显存档

| 阶段 | GPU主要驻留内容 | CPU/磁盘内容 |
| --- | --- | --- |
| 音频特征 | Whisper及当前特征计算 | UNet/VAE权重、视频未解码 |
| 人脸对齐 | 仅必要的单帧变换，检测器继续在CPU | 有界视频帧缓存、人脸数据与矩阵 |
| VAE编码 | VAE、当前窗口输入 | Whisper已卸载；极限档UNet暂存CPU |
| 扩散去噪 | UNet、16帧潜变量及条件 | 极限档VAE暂存CPU，Whisper已卸载 |
| VAE解码 | VAE、当前窗口潜变量 | 极限档UNet暂存CPU |
| 原画面还原/输出 | 标准档最多一个在途帧；压力档不做完整画面GPU还原 | CPU逐帧合成、FFmpeg编码与写盘 |

先做Whisper卸载，再做VAE/UNet按整组件切换。极限档可进一步按UNet子模块卸载，但必须用固定源码和当前Accelerate版本验证hook及设备一致性，不能假定自定义UNet支持全部通用Diffusers开关。

CPU还原优先使用与现有几何变换一致的浮点路径；若改用OpenCV，需要对齐坐标约定、插值、遮罩羽化及色彩范围。通过脸部边缘/位置对比后才可默认启用。VAE tiling和权重量化不纳入首版，避免先引入接缝或量化质量变化。

系统内存建议32GB及以上，16GB内存机器需限制缓存并单独验证权重加载峰值。现有加载可能同时持有FP32 checkpoint和模型副本；可评估 `mmap`/延迟加载以减少CPU峰值，但不能把显存卸载后系统内存无限增长当作成功优化。首轮内存验收同时记录启动和渲染阶段，避免相互掩盖。

## 产品档位与显存调度

模型版本与执行档位分开：模型固定为LatentSync1.6，页面另设“显存策略”。

| 执行档位 | 调度方式 | 画质参数 |
| --- | --- | --- |
| 自动（推荐） | 流式处理；按已验证的显存需求选择标准/节省/极限执行方式 | 保持用户所选步数、guidance、512/16帧 |
| 标准 | 有界流式、现有FP16/VAE slicing、音频编码后卸载 | 相同 |
| 节省显存 | 标准基础上串行引导，必要时启用已验收的前馈分块 | 相同 |
| 极限低显存 | 节省基础上分阶段搬运UNet/VAE，CPU还原 | 相同；耗时增加 |

UI默认高质量候选30步；50步由用户选择，提示耗时增加。执行档位自动变化时不改步数、不改版本，也不出现“1.6失败却产出1.5”的情况。

显存预算和回退边界：

1. 启动前清理本程序TTS，按CUDA可见设备UUID匹配驱动读数，取CUDA/驱动报告的较小空闲值。
2. 保留约1.5～2GiB余量作为首轮调度设计目标；实际启动阈值依据该档位**增量峰值+余量**标定，避免既扣余量又重复加余量。预检时的主进程CUDA上下文和新推理进程上下文应分别记账。
3. 现有标准档7GiB启动检查在新档位实测前保持。不能因“理论上可卸载”就把所有机器门槛直接调到4/5GiB。新档位的峰值和阈值当前均未实测。
4. 每个新档位的首个完整16帧窗口用于预热与测量，长片只在其成功并留足余量后继续。实际生成的首窗口可以提交，不为预热额外重复整段生成。
5. 自动档遇到OOM时，退出该推理进程释放资源，以相同1.6/画质参数提升一档执行策略；最多逐档尝试到极限档，每档只尝试一次。用户固定某个执行档位时默认停止，除非明确开启自动显存策略。
6. 极限档仍失败，或驱动可用显存低于实测最低启动量时，停止并提示释放其他程序占用。禁止无限重试、强杀其他软件、切换1.5、缩小分辨率或缩短时间窗口。
7. OOM只触发显存策略调整；人脸未检测到、磁盘错误、取消和音频损坏不能触发重试。

上述“同一1.6改变执行档位后重试”是本方案拟新增的能力，现有代码仍遵循显存不足直接停止的规则，实施前不改变当前行为。

## 缓存、恢复和输出质量

- 初版支持任务内逐窗口释放，异常时不发布半成品。后续加入按窗口检查点恢复，缓存必须包含输入指纹、源码/权重版本、模型/执行档位、画质参数、全局帧号、噪声模板、随机数状态与对齐状态。
- 自动切换执行档位时，首版从任务起点使用新档位重新生成，复用已验证的原始音频特征/输入缓存。未经验证不直接拼接两个执行档位的成片，以免数值差异形成接缝。
- 同一执行档位的断点恢复先证明与连续执行等价，才启用从最后完成窗口继续。跨档位仅在独立验收后允许断点复用。
- 编码器只接受顺序帧，背压能阻止解码/推理队列继续扩张；stderr持续读取，避免管道堵塞。取消时停止模型和编码器，再清理本次pending文件。
- 高质量输出以CRF16～18作为候选，保持原画面比例，不把更高码率或放大分辨率表述为模型生成细节增加。若源文件已高度压缩，不能保证恢复原本不存在的细节。
- 最终合入用户原始配音，视频流不重复压缩。音频编码兼容时可保留原编码；必须转码时记录编码设置。检查帧数、时间戳、最终时长与音画偏差，不以每片音轨独立拼接替代全局合流。

## 实施拆分与文件落点

维护现有服务/独立runner架构，第三方固定源码不直接打补丁。新增自有流式适配模块，主项目`backend/voxcpm`与根目录`src/voxcpm`同步；本机包在验收后同步。

1. **测量与短窗口节省模式**：runner记录加载、音频、VAE、UNet、还原各阶段显存/内存；卸载Whisper；实现串行引导。先对齐20步参考，再对比30/50步。
2. **有界流式**：新增帧读取/写入和队列；改为当前窗口潜变量；保留全局音频/噪声/RNG/对齐状态；完成长片、取消与尾帧处理。
3. **极限模式**：加入VAE/UNet阶段驻留、CPU还原；按前两阶段测量结果决定是否需要前馈分块。得到新档位实测阈值后再开放自动显存策略。
4. **产品与恢复**：`lipsync_profiles.py`保留硬件检测；`studio_api.py`添加执行档位/质量参数校验；`studio_lipsync.py`负责任务和有界重试；页面显示实际1.6、执行档位、阶段、已完成时长、耗时和失败原因。最后才增加已验收的断点恢复。

推荐新增独立的 `lipsync_streaming.py` / `lipsync_memory.py` 处理流式适配与阶段调度，避免把策略、UI和第三方模型代码堆进同一个函数。具体类名由实现时按现有风格确定。

## 验收标准

| 项目 | 验收方法与通过条件 |
| --- | --- |
| 画质不被隐式降低 | 报告及实际张量确认1.6权重、512、16帧、原guidance和用户步数；16帧尾窗口例外按原语义记录 |
| 短片数值/视觉回归 | 相同输入/种子/20步比较原入口、流式标准、串行引导；记录预测误差及抽帧，不编造“完全无损”或口型分数 |
| 高质量默认 | 正面/轻侧脸、中文/英文、闭嘴和快速发音素材对比20/30/50步；记录清晰度、齿唇伪影、闪烁、音画对齐和耗时，再决定默认值 |
| 时长稳定性 | 1.36秒、10秒、30秒、120秒；热身后渲染显存不随片长线性增长，120秒峰值原则上不高于10秒同形状峰值15%，超出必须定位 |
| CPU内存 | 记录启动峰值和渲染峰值；1080p流式渲染缓存以4GiB以内为首轮设计目标（不含权重加载），实测后再设总RSS预算；队列必须有硬上限 |
| GPU预算 | 每档记录allocated/reserved和驱动空闲量；空闲16GB环境及约8/10GB可用场景验证。先做显式预算/OOM故障注入，再在受控GPU环境验证；不得擅自抢占其他程序显存 |
| 分片接缝 | 检查每16帧与64帧边界、源镜头切换、音频起止、随机尾帧数量；不得出现重复/丢帧、对齐状态重置或音频漂移 |
| 失败与取消 | 每个阶段可取消；OOM有限次提升同一1.6执行档位，极限失败明确停止；无1.5启动、无成功假记录和残留推理进程 |
| 路径与交付 | 中文/空格路径、视频和照片、导出、播放、重载、8种既有主题/尺寸；本机EXE使用当前源码与构建产物 |

测试指标、预算和新档位耗时当前均为设计或待验收项。已有实测仅包括本文开头的1.6短片基线以及原功能验证，不把方案写成已完成实现。完成以上阶段后，再决定是否适合打包发布魔搭更新。
